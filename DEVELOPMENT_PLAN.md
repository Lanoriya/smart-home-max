# План разработки MVP «Умный дом в MAX»

> Исторический план работ. Фактические ограничения и текущий стек описаны в `README.md` и `ARCHITECTURE.md`; этот документ не является описанием реализованных гарантий.

План рассчитан на команду из трёх человек и 6 полноценных рабочих дней. Если разработчик один, этапы сохраняются, а срок реалистично увеличивается до 10–12 дней.

## 1. Роли

- **Backend/Bot:** webhook MAX, FSM, модель данных, matching, уведомления.
- **Frontend/UX:** прототип сценария, административная панель, состояния загрузки и ошибок.
- **Product/QA/DevOps:** интервью и формулировка проблемы, тест-кейсы, Docker/deploy, метрики, README и презентация.

Это зоны ответственности, а не изолированные участки: ежедневная интеграция обязательна.

## 2. Правила работы

- одна основная ветка должна оставаться запускаемой;
- короткие feature-ветки и небольшие pull request;
- каждый сценарий завершается тестом или чек-листом проверки;
- API сначала фиксируется в DTO/OpenAPI, затем одновременно подключаются frontend и backend;
- рабочий demo environment обновляется ежедневно;
- любые новые функции добавляются только после прохождения основного end-to-end сценария.

## 3. Этап 0 — валидация проблемы и дизайн сценария

**Срок:** 0,5–1 день.

### Задачи

- провести минимум 5 коротких интервью с жильцами и 1–2 с представителями УК/диспетчерами;
- зафиксировать текущий процесс As Is: канал обращения, потери, дубли, обратная связь;
- выбрать один приоритетный сегмент и один тип дома для пилота;
- сформулировать проверяемую гипотезу и метрики;
- нарисовать bot-flow и три экрана админки;
- проверить сценарий на 2–3 людях до написания кода;
- утвердить Must/Should/Could/Won't.

### Результат

- одностраничный problem statement;
- схема As Is / To Be;
- кликабельный или бумажный прототип;
- список допущений и рисков;
- готовый сценарий демонстрации.

### Definition of Done

Команда может за одну минуту объяснить, кто пользователь, какая у него проблема, что меняется после внедрения и какой показатель это докажет.

## 4. Этап 1 — каркас и инфраструктура

**Срок:** день 1.

### Backend/Bot

- создать TypeScript-приложение и модульную структуру;
- подключить Prisma/PostgreSQL;
- реализовать модели `user`, `building`, `apartment`, `incident`, `report`, `subscription`, `event`, `bot_session`, `outbox_message`;
- создать первую миграцию и seed;
- добавить `/health/live` и `/health/ready`;
- сделать интерфейс `MessengerAdapter`, чтобы локальный fake и MAX использовали один контракт.

### Frontend/UX

- создать React-приложение;
- собрать layout, login, список и пустую карточку инцидента;
- описать общие типы ответов и ошибок API;
- подготовить состояния loading/empty/error.

### Product/QA/DevOps

- подготовить `compose.yaml`, `.env.example` и команды запуска;
- настроить lint, typecheck и test в CI;
- создать тестовые данные и чек-лист smoke-теста;
- начать README одновременно с кодом.

### Контрольная точка

`docker compose up --build` поднимает БД, backend и статическую админку; seed-данные видны через API.

## 5. Этап 2 — основной сценарий бота

**Срок:** день 2.

### Задачи

- принимать и дедуплицировать webhook-события;
- реализовать `/start`, согласие и привязку по демонстрационному коду;
- создать FSM: категория → зона → описание → фото → подтверждение;
- реализовать поиск похожих инцидентов;
- показать не более трёх кандидатов;
- транзакционно создать новый инцидент либо присоединить report;
- автоматически создать подписку и audit event;
- добавить fake messenger для локального e2e без MAX.

### Тесты

- новый пользователь создаёт инцидент;
- второй пользователь присоединяется;
- пользователь выбирает «не совпадает» и создаёт отдельный инцидент;
- повтор webhook не создаёт дубль;
- просроченная bot-session безопасно начинается заново;
- два параллельных запроса не создают двойное присоединение.

### Контрольная точка

Основной bot-flow полностью работает локально через fake adapter и на тестовом боте MAX.

## 6. Этап 3 — рабочая админка

**Срок:** день 3.

### Backend

- реализовать login/logout и secure session cookie;
- добавить роли dispatcher/supervisor;
- реализовать список, фильтры и карточку инцидента;
- реализовать смену статуса, ответственного, срока и комментария;
- добавить optimistic locking по `version`;
- писать каждое изменение в `incident_events`.

### Frontend

- экран входа;
- таблица: номер, категория, зона, количество обращений, статус, срок, обновление;
- фильтры по статусу, категории и дому;
- карточка с обращениями и историей;
- форма смены статуса/срока с валидацией;
- понятная обработка конфликтов версии и сетевых ошибок.

### Тесты

- неавторизованный пользователь не видит данные;
- dispatcher не может выполнять действие supervisor;
- конфликт двух одновременных изменений не затирает данные;
- изменение статуса создаёт audit event и outbox message.

### Контрольная точка

Диспетчер обрабатывает созданный ботом инцидент без ручной работы с БД.

## 7. Этап 4 — уведомления, надёжность и безопасность

**Срок:** день 4.

### Задачи

- реализовать worker с атомарным захватом сообщений и повторными попытками;
- обеспечить повтор отправки с backoff и dead-letter состоянием;
- добавить идемпотентный ключ уведомления;
- уведомлять подписчиков о принятии, начале работ, переносе срока и устранении;
- добавить кнопки подтверждения результата;
- настроить `scrypt`, rate limits, security headers, CORS и ограничения размера запросов;
- убрать чувствительные данные из логов;
- проверить отсутствие секретов в Git и Docker layers;
- добавить healthcheck контейнеров и корректное завершение процессов.

### Тесты

- временная ошибка MAX приводит к повтору, а не потере уведомления;
- успешное уведомление не отправляется повторно;
- номера квартир не попадают в сообщения другим пользователям;
- токен, пароль и invite-код отсутствуют в логах;
- перезапуск worker не теряет очередь.

### Контрольная точка

Полный путь от изменения статуса до уведомления проходит устойчиво и воспроизводимо.

## 10. Приоритетный backlog

| Приоритет | User story | Проверка |
|---|---|---|
| P0 | Как житель, я создаю обращение в MAX | Инцидент и report появились в БД |
| P0 | Как житель, я вижу похожий инцидент | Бот показывает подходящие варианты |
| P0 | Как житель, я присоединяюсь к проблеме | В инциденте стало два report, дубля нет |
| P0 | Как диспетчер, я вижу очередь | Таблица отражает состояние БД |
| P0 | Как диспетчер, я меняю статус | История и outbox создаются атомарно |
| P0 | Как подписчик, я получаю обновление | Уведомление приходит; при сбое после внешней отправки возможен повтор |
| P1 | Как диспетчер, я переношу срок с причиной | Жители получают новый срок и пояснение |
| P1 | Как житель, я подтверждаю устранение | Ответ виден в карточке инцидента |
| P1 | Как supervisor, я объединяю дубли | Связи и история сохраняются |
| P2 | Как команда, мы видим метрики пилота | Доступны агрегированные показатели |

## 11. Набор обязательных автоматических тестов

### Unit

- фильтрация и ранжирование кандидатов matching;
- допустимые переходы статусов;
- расчёт повторной отправки уведомления;
- редактирование публичного текста без раскрытия персональных данных.

### Integration

- транзакция `incident + report + subscription + event`;
- присоединение к существующему инциденту;
- защита от повторного webhook;
- optimistic locking;
- outbox claim/ack/retry;
- ограничения ролей.

### End-to-end

1. Житель A создаёт проблему.
2. Житель B присоединяется.
3. Диспетчер принимает её в работу.
4. Оба получают уведомление.
5. Диспетчер закрывает проблему.
6. Жители подтверждают результат.

Отдельный smoke-тест выполняется против реального тестового бота MAX.

## 12. Риски и меры

| Риск | Влияние | Мера |
|---|---|---|
| Нет стабильного доступа к MAX API | Блокирует demo | Fake adapter с первого дня, реальная интеграция не позже дня 2 |
| Ошибочное объединение разных проблем | Потеря доверия | Только предложение кандидатов и явный выбор пользователя |
| Недостаточно интервью | Низкая оценка ценности | Провести исследование до фиксации сценария |
| Команда увлечётся функциями | Не готов основной путь | Freeze после P0, P1 только после e2e |
| Сбой внешнего API | Потеря уведомлений | Transactional outbox и retry |
| Утечка данных жильцов | Критический риск | Минимизация данных, роли, audit и отсутствие квартиры в публичных сообщениях |
| Demo зависит от локальной сети | Срыв защиты | Публичный стенд и резервная видеозапись |
