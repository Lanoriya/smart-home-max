# «Дом в порядке» — MVP для MAX

Сервис помогает жителю зарегистрировать проблему в доме через чат-бот MAX, присоединиться к уже открытой общей заявке и получать обновления от диспетчера. Диспетчер работает с одной карточкой инцидента, а не с несколькими одинаковыми обращениями.

## Граница MVP

Приоритетный сценарий: житель подтверждает квартиру → создаёт общую заявку или присоединяется к существующей → диспетчер меняет статус и добавляет комментарий → подписанные жители получают уведомление в MAX.

Личные заявки квартиры изолированы: они не попадают в общий список, не участвуют в подборе совпадений и недоступны соседям. Житель может открыть только свои личные заявки.

Seed для локальной демонстрации добавляет только явно помеченные тестовые аварийные службы, дома, жильцов, автомобили и заявки. Он вынесен в отдельный `compose.demo.yaml` и никогда не запускается production-конфигурацией. Внешних реестров и ГИС ЖКХ в MVP нет.

## Компоненты

- `apps/backend` — REST API, обработка событий MAX и бизнес-логика;
- `apps/backend` worker — очередь уведомлений с повторными попытками;
- `apps/admin-web` — React-диспетчерская;
- PostgreSQL — данные домов, заявок, жителей и очереди;
- MAX Bot API — получение событий и доставка сообщений.

Схема связей и решения описаны в [ARCHITECTURE.md](ARCHITECTURE.md). Контракт API: [openapi.yaml](docs/openapi.yaml). Обязательные проверки API: [DATA-API.yaml](DATA-API.yaml). Инструкции для VDS, эксплуатация и проверка находятся в [DEPLOY_VDS.md](docs/DEPLOY_VDS.md), [OPERATIONS.md](docs/OPERATIONS.md) и [DEMO_SCRIPT.md](docs/DEMO_SCRIPT.md). Для передачи на оценку используйте пошаговую [памятку организаторам](docs/ORGANIZER_HANDOFF.md).

## Локальный запуск

1. Скопируйте `.env.example` в `.env` и задайте десятизначный `RESIDENT_UK_CODE`.
2. Замените демонстрационные значения `POSTGRES_PASSWORD`, `APARTMENT_CODE_PEPPER`, `ADMIN_SEED_PASSWORD` и webhook-секреты.
3. Запустите все компоненты одной командой:

   ```bash
   docker compose -f compose.yaml -f compose.demo.yaml up --build
   ```

4. Откройте `http://localhost:8080`; используйте тестовую учётную запись из `ADMIN_SEED_USERNAME` / `ADMIN_SEED_PASSWORD`.

Остановка: `docker compose -f compose.yaml -f compose.demo.yaml down`. Для остановки с удалением тестовой БД добавьте `-v` — это удалит все локальные данные. Запуск только инфраструктуры без тестового наполнения выполняется обычным `docker compose up --build`.

Проверки исходников:

```bash
pnpm typecheck
pnpm test
pnpm build
```

## MAX: локальная проверка и production

`MAX_MODE=fake` не обращается в сеть: сообщения пишутся в структурированный лог. Для реального MAX заполните секреты только в локальном `.env`/секрет-хранилище:

```dotenv
MAX_MODE=api
MAX_RECEIVE_MODE=webhook
MAX_BOT_TOKEN=...
MAX_WEBHOOK_SECRET=...
MAX_PUBLIC_WEBHOOK_URL=https://api.example.ru/webhooks/max
ADMIN_COOKIE_SECURE=true
ADMIN_WEB_ORIGIN=https://dispatcher.example.ru
```

Long Polling используйте лишь в разработке. Production-диспетчерская и webhook используют единый публичный адрес `https://APP_DOMAIN`.

Production-конфигурация подготовлена в `compose.production.yaml`: Caddy автоматически получает TLS-сертификат, БД не публикуется наружу, миграции и bootstrap первого supervisor выполняются до запуска API. Для передачи организаторам используйте архив `release/smart-home-max-production.zip`: он не содержит паролей, токенов, данных БД и собранных артефактов. Точная команда и порядок настройки приведены в `docs/DEPLOY_VDS.md`.

## Проверочный сценарий

1. Создайте дом и проверьте адрес в диспетчерской.
2. Назначьте индивидуальный код квартире в разделе «Квартиры»; пользователь вводит его после кода УК. Индивидуальный код хранится только как хеш и не отображается повторно.
3. Два жителя одного дома создают/поддерживают одну общую проблему.
4. В диспетчерской откройте инцидент, измените статус и добавьте комментарий.
5. Убедитесь, что оба жителя получили уведомление, а житель другого дома не может открыть или поддержать заявку.
6. Создайте заявку «Проблема моей квартиры» и убедитесь, что она не появляется в «Общих заявках дома».

## Данные и безопасность

- пароли администраторов хешируются `scrypt`, сессии хранятся как SHA-256-хеши и передаются через HttpOnly SameSite cookie;
- токены и пароли не входят в Docker build context и должны храниться только в `.env`/`.env.production` или секрет-хранилище; перед передачей архива исключите env-файлы, дампы и логи;
- телефоны по умолчанию скрыты. Их показ в поиске автомобиля требует отдельного подтверждения пользователя; добавлять чужой номер можно только с согласием владельца;
- для реального запуска необходимы политика обработки персональных данных, сведения об операторе и отдельная проверка правового основания обработки;
- доставка очереди имеет семантику **как минимум один раз**: при сбое после внешней отправки повторное уведомление возможно.
- смена кода УК, удаление домов, редактирование квартир, справочника и массовые рассылки записываются в административный аудит; смена кода УК и удаление дома доступны только supervisor.

## Ограничения MVP

- доступ администратора пока не разделён по нескольким УК и домам: это модель одной управляющей организации;
- индивидуальный код квартиры должен быть задан диспетчером для каждого реального дома; без него остаётся только демонстрационный общий код УК;
- нет интеграций с ГИС ЖКХ, поставщиками коммунальных услуг и официальными реестрами;
- списки в текущем интерфейсе ограничены 100 инцидентами/квартирами и 10 личными заявками/комментариями, полноценной пагинации пока нет;
- версия схемы `DATA-API.yaml` должна быть сверена с актуальным пакетом организаторов перед сдачей.
